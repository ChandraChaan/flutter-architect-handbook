# Contributing

Thanks for helping make the handbook better!

## Fixing an answer

If an answer is wrong, unclear or out of date (Flutter moves fast), open a pull request that changes it, and explain why in the description, ideally with a link to the Flutter or Dart docs or the source.

## Adding a question

Add it to the chapter it fits, in this format:

```markdown
### 🟡 The question, phrased the way an interviewer or teammate would ask it?

A direct answer first, in a few sentences. Then the trade-offs or the
"it depends" part, a short code sample if it helps, and what a strong
answer shows.
```

Pick the level honestly:

- 🟢 **Junior**: something every Flutter developer should know.
- 🟡 **Senior**: needs production experience or trade-offs.
- 🔴 **Architect**: about systems, teams or long-term decisions.

Keep answers short and in your own words. Please don't copy text from books, courses or other sites. Then update the question counts in the README table.

## Style

- Plain, direct language. Define jargon the first time you use it.
- Code samples must compile with current stable Flutter.
- Prefer "do this, because…" over lists of facts.
